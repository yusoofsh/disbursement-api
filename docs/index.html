01Overview

A disbursement service engineered around one question: what happens when things go wrong at the worst moment? Duplicate client retries, two admins approving at once, audit writes failing mid-request, tokens leaking after logout. The design answers each with a database-backed guarantee rather than application-level hope.

02System Architecture

A single Fastify instance fronts PostgreSQL. Every request gets a UUID request id (echoed as X-Request-ID), passes rate limiting, JWT authentication, and a role guard before touching a service. Audit writes happen after the primary transaction commits — a failure there is logged, never propagated.

03Idempotency — Safe Retries

POST /disbursements accepts an optional Idempotency-Key (UUID). The key is scoped per user via UNIQUE(user_id, idempotency_key); the payload is normalized to a fixed field order and SHA-256 hashed. The exact response (status + body) is persisted for 24 hours — never in memory, so replays survive restarts and horizontal scaling. Two simultaneous first uses are serialized by a transaction-scoped advisory lock.

…
guarantee

Byte-identical replay

The stored response body is returned verbatim with X-Idempotent-Replayed: true. No second disbursement, no second audit event.

guarantee

Payload mismatch → 409

Same key, different normalized payload returns IDEMPOTENCY_KEY_REUSED — the client learns its retry drifted instead of silently double-paying.

trade-off

Storage for certainty

Full response bodies are stored for 24h and expired rows are replaced on reuse. A cleanup job is possible but intentionally omitted.

Why not in-memory? A process-local cache breaks across instances and vanishes on restart — precisely when clients retry most. The unique constraint plus advisory lock makes PostgreSQL the single arbiter, so the guarantee holds no matter how many app instances run.
04Concurrency — Exactly One Winner

Status transitions use an atomic compare-and-set: the WHERE status = 'PENDING' predicate is evaluated by PostgreSQL while updating. Under a race, the first update locks and changes the row; every other request matches zero rows and gets a typed 409 DISBURSEMENT_NOT_PENDING — never a generic 500. 

UPDATE disbursements
SET status = $1, approved_by = $2, updated_at = NOW()
WHERE id = $3
  AND status = 'PENDING'      -- the compare-and-set predicate
  AND deleted_at IS NULL
RETURNING *;                  -- zero rows ⇒ follow-up lookup: 404 vs 409

…
chosen

Optimistic CAS (one round trip)

  • No time-of-check-to-time-of-use window
  • Row lock held only for the update itself
  • No app-level coordination — scales across instances
  • Simple under high contention
rejected

Read-then-write / SELECT FOR UPDATE

  • Read-then-write without a lock has a race window — both requests can read PENDING and both "win"
  • FOR UPDATE serializes contenders inside a longer transaction and blocks while held
  • CAS cost: one follow-up lookup to distinguish 404 from 409
05Authentication Lifecycle

Access tokens live 15 minutes; refresh tokens 7 days. Only the SHA-256 hash of a refresh token is stored. Refresh rotates: the presented token is revoked and a fresh pair issued. Logout sets revoked_at; any reuse fails with 401. Passwords use Argon2id.

07Data Model

Five tables, UUID keys throughout. Integrity lives in the database: check constraints on amount, fee, status and role; partial indexes on live (deleted_at IS NULL) rows; audit rows deliberately have no foreign key to disbursements so the trail outlives the data.

indexing

Partial indexes

(status, created_at DESC), (created_at DESC), (amount) — all WHERE deleted_at IS NULL, matching every list query's filter.

integrity

Defense in depth

App validates with JSON Schema; the database re-checks with constraints. A buggy deploy cannot write a negative amount or an unknown status.

deliberate

No audit FK

audit_logs.entity_id carries no cascading foreign key — soft-deleted or purged rows must never take the audit trail with them.

08Audit Logging — Honest Non-Blocking

The spec requires audit failure to never block the main operation. The implementation takes the simplest honest reading: commit the primary transaction first, then insert the audit row; on failure, log a structured error with request_id, entity and action — and still return success.

what this buys

Availability of the money path

An audit-table outage can never block an approval. Every mutation — created, status_changed, deleted — is attempted with before/after jsonb snapshots and the originating request id.

what it costs

Possible audit loss

A failed insert is lost (only logged). This is documented, not hidden: the production evolution is a transactional outbox — write the event in the same transaction, deliver via a background worker.

Observability contract. Every request emits structured JSON logs carrying reqId, method, path, status and latency; the same id is returned as X-Request-ID on every response — including 4xx/5xx — so a client-reported id greps straight to the full request trace. Passwords, tokens and JWTs are never logged.
